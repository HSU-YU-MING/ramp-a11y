## 一、專案概述

**一句話定位**：讓開發者在自己的瀏覽器裡，一鍵掃描任何網頁的無障礙問題，並用繁中清楚說明「哪裡有障礙、為什麼、怎麼修」，同時對應到台灣官方規範的準則與檢測等級。

**專案性質**：個人作品集專案（Portfolio Project）。目標不是營利，而是展示技術深度、領域知識與工程完成度。

**為什麼是這個題目**
- 開發者本身具政府系統的 WCAG 焦點管理與無障礙修正實務經驗，是真實累積、非臨時挑選的領域。
- 題材同時具備「國際標準（WCAG）」與「台灣在地法規」兩層，後者是相對國外開發者的獨有優勢。
- 成品可實際拿去測試台灣政府與企業網站，展示素材充足、說服力高。

## 二、背景與動機

### 標準現況
- 現行國際標準為 **WCAG 2.2**（W3C，2023 年 10 月發布），採 4 大原則、A/AA/AAA 三個符合等級。
- **WCAG 3.0** 仍在草案階段，預計 2028–2030 才會成為正式標準，因此以 2.2 為基礎開發不會過時。
- **台灣「網站無障礙規範」**：2017 年正式實施，參考 WCAG 制定，採 13 指引、78 成功準則、A/AA/AAA 三個檢測等級，主管機關為數位發展部。
- **法源依據**：2011 年《身心障礙者權益保障法》將「公共資訊無障礙」入法，政府網站必須符合規範；標章效期三年，到期需重新檢測申請。

### 需求現況
- 依 WebAIM 大規模掃描，全球前一百萬個首頁中約 **95.9%** 至少存在一項可被自動偵測的 WCAG 失敗。
- 「幾乎每個網站都不合格」——需求持續存在、展示素材永不缺乏。

## 三、市場分析

### 既有工具
| 工具 | 型態 | 特性 | 缺口 |
|------|------|------|------|
| axe (Deque) | 引擎 / 擴充套件 | 業界標準檢測引擎，開源 | 純技術報告、英文、不對應台灣規範 |
| WAVE | 網頁 / 擴充套件 | 視覺化標示 | 英文為主、不對應台灣規範 |
| Lighthouse | Chrome 內建 | 綜合稽核含無障礙 | 分數導向、解說淺、非在地化 |
| Freego | 單機軟體 | 台灣官方指定檢測工具 | 老派桌面軟體、體驗差、非現代流程 |

### 市場空隙（差異化來源）
1. **在地化空白**：國際工具的結果對應不到台灣的「檢測碼／標章」制度，開發者看完仍需自行翻譯比對。
2. **官方工具體驗落後**：Freego 為單機軟體，介面與流程不符合現代開發習慣。
3. **缺乏教育性**：多數工具僅輸出錯誤代碼，未解釋「為何構成障礙、如何修正」。

### 本專案定位
> 一款**現代、瀏覽器內執行、以繁中解說、並對應台灣規範**的無障礙檢測器。三點疊加即與 axe／WAVE／Lighthouse 形成明確區隔，並在體驗層面超越 Freego。

| 使用者 | 情境 |
|--------|------|

## 五、產品範圍（做什麼 / 不做什麼）

### MVP 要做（In Scope）
- Manifest V3 Chrome 擴充套件。
- 掃描「當前分頁、渲染後的 DOM」。
- 以 axe-core 為引擎，取得 violations 與 incomplete。
- 透過對應表轉譯為台灣規範編號、等級、繁中解說。
- 結果面板：依 A/AA/AAA 分組、統計數字、點擊定位高亮。
- 標示「需人工複核」項目。
- 15 條常見規則的繁中對應內容。

### MVP 不做（Out of Scope，明確排除避免發散）
- 不做貼網址／後端代抓（會漏測渲染後內容，且要主機）。
- 不做多頁 / 全站爬取。
- 不做報告匯出（PDF/HTML）。
- 不做帳號、雲端儲存、任何後端。
- 不補滿 78 條準則（先 15 條）。
- 不做自動修復（只指出問題與建議，不改別人的頁面）。

以上「不做」皆為刻意，避免範圍蔓延拖垮 MVP。第二、三階段再談。

## 六、核心功能規格

檢測引擎採用開源 **axe-core**（不自行重造）；本專案價值集中在其上的四層加值：

1. **台灣規範對應**：將 axe 規則對應到台灣「網站無障礙規範」的準則編號與 A/AA/AAA 檢測等級。此對應表是核心獨有資產。
2. **繁中教育式解說**：每個問題說明「為什麼構成障礙 + 建議修正方式」，而非僅顯示錯誤代碼。
3. **頁面即時定位**：點選問題項目，即在頁面上高亮對應的出錯元素並捲動到該位置。
4. **自動 / 人工分流標示**：清楚標明哪些可由軟體自動判定、哪些必須人工複核，不給「已完全合規」的誤導結論。

## 七、使用者流程

```
1. 使用者在任一網頁點擊工具列的 ramp-a11y 圖示
2. 彈出 popup，顯示「開始檢測」按鈕（初始狀態）
3. 按下按鈕 → 顯示「檢測中…」載入狀態
4. 背後：注入 axe-core 到當前分頁 → 執行掃描 → 回傳結果
5. popup 顯示結果面板：
     - 頂部統計：違規總數、A/AA/AAA 各數量、需人工複核數
     - 清單：依等級分組，每項顯示繁中標題 + 台灣準則編號 + 等級標籤
6. 使用者點擊某一項 → 展開繁中解說（為什麼 / 如何修）
                        → 同時在原頁面高亮對應元素並捲動過去
7. 使用者可再次按「重新檢測」
```

**錯誤與邊界情況**
- 在 `chrome://`、擴充套件商店等受保護頁面無法注入 → 顯示友善提示「此頁面無法檢測」。
- 頁面完全無違規 → 顯示正向訊息（並提醒仍需人工複核）。
- 注入失敗 / 逾時 → 顯示錯誤狀態與「重試」。

## 八、畫面與介面規格

僅有單一 popup 介面，包含四種狀態：

### 狀態 A：初始
- 標題列：Ramp 標誌 + 名稱。
- 主體：一句簡短說明 + 大顆「開始檢測」按鈕。

### 狀態 B：載入中
- 置中的載入指示 + 「檢測中…」文字。

### 狀態 C：結果
- **統計列**（置頂固定）：
  - 違規總數（大字）
  - 三個等級徽章：A ●　AA ●　AAA ●（各附數量）
  - 「需人工複核 N 項」
- **問題清單**（可捲動）：依 A → AA → AAA 分組，每組有標題。
  - 單筆項目（收合狀態）：等級標籤 + 繁中標題 + 台灣準則編號 + 影響元素數。
  - 單筆項目（展開狀態）：加上「為什麼是障礙」「如何修正」兩段繁中；每個受影響元素一列，點擊即在頁面高亮。
- **底部**：「重新檢測」按鈕。

### 狀態 D：無法檢測 / 錯誤
- 圖示 + 說明文字 + （若適用）重試按鈕。

### 視覺設計原則
- 乾淨、現代、留白充足；等級用一致的顏色系統（例如 A 最嚴重用暖色、AAA 用中性色，並確保**工具本身也符合對比規範**——這是加分細節）。
- popup 寬度建議 380–420px，高度自適應並可捲動。
- 全繁中介面。

## 九、技術架構

### 關鍵決策：為何選擇「瀏覽器擴充套件」
無障礙檢測必須測試 **JavaScript 執行後、實際渲染完成的 DOM**。現代網站多為 SPA 或大量前端渲染，原始 HTML 常為空殼。
- **後端 proxy 代抓** 與 **貼上 HTML** 取得的都是原始 HTML（JS 執行前），會嚴重漏測 → **排除**。
- **瀏覽器擴充套件** 直接在當前分頁的實際渲染結果上執行 → **正解**。

附帶優勢：零基礎設施（免主機、免金流）、技術亮點高、可直接測真實台灣政府網站。唯一代價是安裝門檻，用 GIF ＋ 安裝說明即可克服。

### 技術棧
- **平台**：Chrome / Edge 擴充套件，**Manifest V3**。
- **語言**：Vanilla JavaScript（保持輕量，不引入前端框架）。
- **檢測引擎**：axe-core，**本地打包**於 `vendor/axe.min.js`（MV3 的 CSP 不允許遠端載入並執行腳本）。
- **注入方式**：`chrome.scripting.executeScript`。
- **權限**：`activeTab`、`scripting`；`host_permissions` 視需要設 `<all_urls>`。

**各檔職責摘要**
- `popup.js` 是大腦：按下按鈕 → 用 `executeScript` 注入 `vendor/axe.min.js` 與 `content/scanner.js` 的掃描函式 → 拿到結果 → 載入 `rules-map.json` 轉譯 → 渲染面板。
- `content/scanner.js` 提供兩個能力：在頁面上下文執行 axe 掃描並回傳純資料；以及依傳入的 CSS selector 對元素加上高亮外框並捲動過去。
- `rules-map.json` 是唯一需要領域知識維護的資料檔，與程式邏輯分離。

## 十一、訊息傳遞與注入設計

MV3 下，popup 本身即擁有 `scripting` 權限，可直接對當前分頁注入，流程如下：

**掃描**
1. `popup.js` 取得當前分頁 `tabId`。
2. `chrome.scripting.executeScript` 注入 `vendor/axe.min.js`（讓頁面擁有 `axe` 全域物件）。
3. 再 `executeScript` 執行一段函式：呼叫 `axe.run()`，回傳 `results.violations` 與 `results.incomplete`（只回傳序列化後的純資料：規則 id、影響元素的 target selector、原始說明等）。
4. `popup.js` 收到後，用 `rules-map.json` 對照轉譯並渲染。

**高亮定位**
1. 使用者在 popup 點某個受影響元素（該元素帶有 axe 給的 target selector）。
2. `popup.js` 以 `executeScript` 執行高亮函式，傳入 selector。
3. 頁面上找到元素 → 加上外框樣式 → `scrollIntoView`。再次點擊或重新掃描時清除舊高亮。

> MVP 不一定需要長駐 content script 與 background；上述以 `executeScript` 即可完成。`service-worker.js` 先保留為極簡檔，供日後擴充。

## 十二、資料結構定義

### 對應表單筆（rules-map.json 內每個元素）
```json
{
  "axeRuleId": "color-contrast",
  "twGuideline": "1.4.3",
  "twLevel": "AA",
  "category": "可感知",
  "titleZh": "文字與背景對比不足",
  "whyZh": "低對比會使弱視或高齡使用者難以辨識文字內容。",
  "howZh": "將文字與背景對比提高至 4.5:1（大型文字 3:1）以上。"
}
```

### 掃描後、給 UI 用的單筆結果（程式內組出）
```json
{
  "axeRuleId": "image-alt",
  "twGuideline": "1.1.1",
  "twLevel": "A",
  "category": "可感知",
  "titleZh": "圖片缺少替代文字",
  "whyZh": "...",
  "howZh": "...",
  "localized": true,
  "nodes": [
    { "target": "img.logo", "html": "<img class=\"logo\" ...>" }
  ]
}
```
- `localized`：此規則是否已在對應表中。若否 → 顯示 axe 原始英文並標「（尚未在地化）」。
- `nodes`：受影響元素陣列，`target` 為高亮用的 selector。

## 十三、規則對應表（MVP 15 條完整內容）

> 台灣「網站無障礙規範」的成功準則編號沿用 WCAG 架構，故對應編號與 WCAG 成功準則一致。以下可直接作為 `rules-map.json` 的初版內容。

| # | axe 規則 | 準則 | 等級 | 原則 | 繁中標題 |
|---|----------|------|------|------|----------|
| 1 | color-contrast | 1.4.3 | AA | 可感知 | 文字與背景對比不足 |
| 2 | image-alt | 1.1.1 | A | 可感知 | 圖片缺少替代文字 |
| 3 | document-title | 2.4.2 | A | 可操作 | 網頁缺少標題 |
| 4 | html-has-lang | 3.1.1 | A | 可理解 | 未標示網頁語言 |
| 5 | label | 4.1.2 | A | 強健 | 表單欄位缺少標籤 |
| 6 | link-name | 2.4.4 | A | 可操作 | 連結沒有可辨識文字 |
| 7 | button-name | 4.1.2 | A | 強健 | 按鈕沒有可辨識名稱 |
| 8 | heading-order | 1.3.1 | A | 可感知 | 標題階層順序錯亂 |
| 9 | list | 1.3.1 | A | 可感知 | 清單結構不正確 |
| 10 | frame-title | 4.1.2 | A | 強健 | iframe 缺少標題 |
| 11 | aria-required-attr | 4.1.2 | A | 強健 | ARIA 缺少必要屬性 |
| 12 | aria-valid-attr-value | 4.1.2 | A | 強健 | ARIA 屬性值無效 |
| 13 | duplicate-id | 4.1.1 | A | 強健 | 出現重複的 id |
| 14 | link-in-text-block | 1.4.1 | A | 可感知 | 連結僅以顏色區辨 |
| 15 | focus-visible（人工複核傾向）| 2.4.7 | AA | 可操作 | 鍵盤焦點不明顯 |

各筆的 `whyZh` / `howZh` 建議內容：

1. **對比不足**：低對比使弱視、高齡或強光環境下的使用者難以閱讀 → 文字對比提高至 4.5:1（大型文字 3:1）以上。
2. **圖片替代文字**：螢幕報讀軟體無法描述無 alt 的圖片，視障者將錯過資訊 → 為有意義的圖片加上描述性 alt；純裝飾圖用空 alt（`alt=""`）。
3. **網頁標題**：無標題時，報讀軟體與分頁列無法告知使用者所在頁面 → 於 `<title>` 填入清楚描述該頁的標題。
4. **網頁語言**：未設 `lang` 時報讀軟體可能以錯誤語音朗讀 → 在 `<html lang="zh-Hant">` 標示正確語言。
5. **表單標籤**：欄位無標籤時，使用者不知該欄要填什麼 → 用 `<label for>` 或 `aria-label` 明確關聯。
6. **連結文字**：空連結或僅圖示的連結，報讀軟體只念得出「連結」 → 提供描述目的的文字或 `aria-label`。
7. **按鈕名稱**：無文字的按鈕無法被辨識用途 → 補上可見文字或 `aria-label`。
8. **標題階層**：跳階（如 h1 直接到 h4）破壞內容結構理解與導覽 → 依內容層級循序使用標題。
9. **清單結構**：用非清單標記假裝清單，報讀軟體無法正確導覽 → 用 `<ul>`／`<ol>`／`<li>` 正確標記。
10. **iframe 標題**：無標題的 iframe 讓使用者不知內嵌內容為何 → 加上 `title` 屬性描述用途。
11. **ARIA 必要屬性**：ARIA 角色缺少必填屬性會導致輔助科技解讀錯誤 → 補齊該角色所需的 ARIA 屬性。
12. **ARIA 屬性值無效**：無效值使輔助科技行為不可預期 → 依規範填入合法值。
13. **重複 id**：重複 id 會使標籤關聯、腳本與輔助科技指向錯亂 → 確保每個 id 在頁面唯一。（註：WCAG 2.2 已移除對應的 4.1.1「剖析」，但台灣現行規範仍沿用，故保留。）
14. **僅以顏色區辨**：只靠顏色標示連結，色覺障礙者無法分辨 → 另加底線或其他非顏色線索。
15. **焦點可見**：鍵盤操作者看不到目前焦點就無法導覽 → 保留或加強 `:focus` 的可見樣式（此項多需人工確認實際視覺效果）。

---

## 十四、誠實面對的限制

- 自動化檢測僅能涵蓋約 **三到四成** 的無障礙問題（對比、alt 缺失、標籤結構、焦點可見等）。
- 「替代文字寫得是否恰當」「閱讀順序是否合理」等仍需人工判斷。
- 本工具的角色是**輔助自檢與教育**，不等同官方標章認證，也不能取代人工複核。

> 將此限制明確標示於產品與文件中，反而展現對領域的成熟理解，是作品集的加分項。

## 十五、開發里程碑與驗收標準

### 里程碑 M1：可掃描的骨架（核心）
**任務**
- 建立 `manifest.json`（MV3、權限、popup、圖示）。
- popup 放一顆「開始檢測」按鈕。
- 下載 axe-core 放入 `vendor/axe.min.js`。
- `popup.js` 注入 axe 並執行 `axe.run()`，將結果印到 console。

**驗收**：在一般網頁點擊擴充套件，console 能印出 axe 的 violations 陣列。

### 里程碑 M2：結果面板
**任務**
- 把 console 結果改為在 popup 面板呈現。
- 依 A/AA/AAA 分組，頂部顯示統計數字。
- 每項可展開／收合。

**驗收**：面板正確列出違規、分組與數量正確、可展開看細節。

### 里程碑 M3：在地化與解說
**任務**
- 建立 `data/rules-map.json`（第十三節 15 條）。
- 掃描結果經對應表轉譯：顯示繁中標題、台灣準則編號、等級、為什麼／如何修。
- 未在對應表的規則標「（尚未在地化）」。

**驗收**：15 條常見規則出現時皆顯示繁中解說；其餘規則仍顯示且有標註。

### 里程碑 M4：頁面定位高亮
**任務**
- 點擊結果中的受影響元素，在頁面高亮並捲動過去。
- 重新掃描或再次點擊時清除舊高亮。

**驗收**：點任一元素能準確高亮到頁面對應位置。

### 里程碑 M5：收尾與作品集化
**任務**
- 加入「需人工複核」標示、無違規／錯誤狀態、受保護頁面提示。
- 介面樣式打磨（含工具本身符合對比）。
- 撰寫 README：定位、截圖、安裝說明、限制聲明。
- 錄製操作 GIF；挑一個真實台灣政府網站做實測案例。

**驗收**：陌生人依 README 能自行安裝並跑出結果；README 具備截圖與誠實限制說明。

### 後續階段（非 MVP）
- **第二階段**：對應表擴充至主要 78 準則；報告匯出（PDF/HTML）；深色模式；i18n。
- **第三階段（v2）**：後端無頭瀏覽器（Puppeteer）渲染後檢測，達成「貼網址即測」；多頁 / 全站掃描。

## 十七、風險與因應

| 風險 | 因應 |
|------|------|
| 規則對應表工作量大 | MVP 先做 15 條（本文件已備好），漸進擴充 |
| axe-core 版本更新導致規則異動 | 鎖定 axe 版本，升級時統一校對對應表 |
| 擴充套件安裝門檻影響展示 | 以 GIF 與清楚文件降低理解成本；v2 再補分享版 |
| 台灣規範未來改版 | 對應表為獨立資料檔，改版時集中更新 |
| 範圍蔓延 | 嚴守第五節「不做」清單，多的想法一律排入第二/三階段 |
| 高亮 selector 對不到動態元素 | 掃描後即時取得 selector；重新掃描前清除舊狀態 |
