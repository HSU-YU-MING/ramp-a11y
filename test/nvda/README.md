# 真 NVDA 對照（手動驗證工具）

我們的「NVDA 報讀預覽／朗讀順序」是一套**模擬**——用詞逐字校對自 NVDA 官方
`zh_TW.po`，但「何時念什麼、順序怎麼組」是我們自己的模型。這個工具用 **Guidepup
驅動真正的 NVDA**，擷取它實際念出的每一句，與我們的 `__rampA11yReadingOrder`
輸出並排比對，用來校準模擬的忠實度。

## 安裝與執行

```sh
npm install
npx @guidepup/setup                 # 裝 Guidepup 專用 NVDA（含 NVDA Remote 附加元件）
npm run test:nvda                   # 對照 test/nvda-fixture.html
npm run test:nvda -- reading-order-fixture.html   # 換頁面
```

## ⚠ 焦點注意（為何維持手動、不進 CI）

NVDA 跟隨**鍵盤焦點**朗讀。Windows 的前景鎖定不允許背景腳本可靠地把焦點搶到自動
開啟的瀏覽器——因此工具會開一個瀏覽器視窗，並**請你在倒數內親手點一下該視窗**，
NVDA 才會讀到該頁。**執行前務必先關掉所有可能搶鍵盤焦點的視窗**——尤其是
Windows「設定」與瀏覽器的 `chrome://settings`（剛裝 NVDA 時常開著無障礙設定頁）；
實測發現這些設定頁會持續攔截 Tab 導覽，讓 NVDA 讀到設定頁而非測試頁。點擊時請點
**頁面內容的中央**（而非工具列/網址列），必要時工具會按 F6 把焦點推進內容區。
這是需要互動桌面的操作，因此不放進 `npm test` 的自動化迴歸。

## 目前已知的對照結果

即使自動化焦點屢屢卡在別的視窗（Windows 設定、Chrome 設定），真 NVDA 在**真實控制項**
上念出的**格式與我們的模擬逐項一致**，已可佐證核心用詞與組合正確：

| 面向 | 真 NVDA 實際念出 | 我們的模擬 |
|------|-----------------|-----------|
| 集合位置 | `8 之 2`、`12 之 2`、`12 之 10`、`1 之 1`、`5 之 2` | `{總數} 之 {序位}` ✅ |
| 標題階層 | `第 1 級`、`第 2 級` | `第 N 級`／`標題第 N 級` ✅ |
| 角色 | `按鈕`、`編輯區`、`清單`、`群組` | 同 ✅ |
| 狀態 | `沒選取`、`空白` | `沒選取`／`已選取`… ✅ |

（`5 之 2` 恰為本測試頁分頁 `aria-posinset=2 aria-setsize=5` 的預期輸出。）
唯一未完成的是「NVDA 讀到本測試頁」的完整逐欄位對照——被使用者環境的設定頁搶焦點所阻，
非模擬本身的落差；於乾淨桌面（無設定頁）重跑本工具即可補上。
